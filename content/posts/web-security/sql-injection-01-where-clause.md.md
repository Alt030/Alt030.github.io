## 1. 개요

이번 글에서는 **WHERE 절에서 발생하는 SQL Injection**에 대해 공부한다.

---

## 2. 배경 지식

### 2.1 SQL이란?

SQL(Structured Query Language)은 데이터베이스에 저장된 데이터를 **조회하거나 추가, 수정, 삭제하기 위해 사용하는 언어**이다.

웹 애플리케이션에서는 서버가 데이터베이스에 데이터를 조회하거나 저장할 때 SQL을 사용할 수 있다.

### 2.2 SQL Query란?

SQL을 사용하여 데이터베이스에 요청하는 명령문을 **쿼리(Query)** 라고 한다.

데이터를 조회할 때 사용하는 `SELECT`문의 기본적인 형태는 다음과 같다.

```sql
SELECT 열이름 FROM 테이블이름;
```

`SELECT`문은 쉽게 말해 **"어떤 테이블에서(FROM) 원하는 열의 데이터를 가져와라(SELECT)"** 라는 의미로 이해할 수 있다.

예를 들어 다음과 같은 Query가 있다고 가정해보자.

```sql
SELECT * FROM products;
```

- `SELECT` : 조회할 열을 지정한다.
- `FROM` : 데이터를 조회할 테이블을 지정한다.
- `*` : 해당 테이블의 모든 열을 선택한다.

따라서 위 Query는 `products` 테이블의 **모든 열을 조회**한다는 의미이다.

### 2.3 WHERE 절이란?

앞에서는 `products` 테이블의 모든 데이터를 조회했다.

> 그렇다면 모든 데이터가 아니라 **특정 조건에 맞는 데이터만 조회하려면 어떻게 해야 할까?**

이때 사용하는 것이 `WHERE` 절이다.

`WHERE` 절은 **특정 조건을 만족하는 행만 조회할 때 사용**한다.

예를 들어 `category`가 `Gifts`인 행을 조회하는 Query는 다음과 같다.

```sql
SELECT *
FROM products
WHERE category = 'Gifts';
```

위 Query는 `products` 테이블에서 `category`의 값이 `Gifts`인 행만 조회한다.

### 2.4 사용자 입력과 SQL Query

> 그런데 웹 애플리케이션에서는 `Gifts`라는 값이 어디서 오는 걸까?

웹 애플리케이션에서는 사용자의 입력값을 서버로 전달하고, 서버가 이 값을 데이터베이스 조회에 사용할 수 있다.

예를 들어 사용자가 `Gifts` 카테고리를 선택했을 때 다음과 같은 흐름으로 처리될 수 있다.

```text
사용자가 Gifts 카테고리 클릭
        ↓
HTTP 요청
GET /filter?category=Gifts
        ↓
서버가 category 값 확인
        ↓
DB 조회에 사용
        ↓
SELECT *
FROM products
WHERE category = 'Gifts';
```

여기서 사용자가 선택한 `Gifts`는 HTTP 요청의 `category` 파라미터를 통해 서버로 전달되고, 서버는 이 값을 SQL Query의 조건으로 사용할 수 있다.

즉, **사용자가 전달한 값이 서버에서 SQL Query를 구성하는 데 사용될 수 있다.**

### 2.5 SQL Injection이란?

> 그렇다면 사용자가 `category`의 값을 임의로 조작할 수 있고, 이 값이 SQL Query에 안전하게 처리되지 않은 채 사용된다면 어떻게 될까?

개념을 이해하기 위해 사용자가 다음과 같은 값을 입력했다고 가정해보자.

```text
' OR 1=1 --
```

이 값이 SQL Query에 그대로 사용된다면 Query의 구조는 다음과 같이 변할 수 있다.

```sql
SELECT *
FROM products
WHERE category = '' OR 1=1 -- ';
```

`--`는 이후 내용을 주석으로 처리할 때 사용한다.

> **Note**
>
> 주석 문법은 DBMS에 따라 차이가 있으며, 이에 대해서는 이후에 다룬다.

여기서 `WHERE` 절의 조건을 살펴보면 두 개의 조건식이 `OR`로 연결되어 있다.

```text
category = '' OR 1=1
```

두 조건을 나누어 보면 다음과 같다.

| 조건 | 의미 | 결과 |
| --- | --- | --- |
| `category = ''` | category가 빈 문자열인지 확인 | 상황에 따라 다름 |
| `1 = 1` | 1과 1이 같은지 확인 | 항상 참 |

`OR` 연산은 두 조건 중 하나라도 참이면 전체 조건이 참이 된다.

`1=1`은 항상 참이므로 `category`의 값과 관계없이 전체 조건은 참이 된다.

결과적으로 `WHERE` 조건이 모든 행에서 참이 되어 `products` 테이블의 모든 행이 조회될 수 있다.

> **핵심**
>
> SQL Query에 들어가야 할 단순한 사용자 데이터가 **SQL 문법으로 해석되어 Query의 구조를 변경할 수 있게 된 것**이다.

이것이 **SQL Injection**이라고 할 수 있다.

## 4. 분석

### 4.1 관찰

문제 사이트에 접속하면 여러 상품과 상품을 분류하기 위한 카테고리를 확인할 수 있다.

![[Pasted image 20260902164224.png]]

`Gifts` 카테고리를 선택하면 해당 카테고리에 속하는 상품만 화면에 표시된다.

이때 브라우저의 요청 URL을 확인하면 다음과 같이 `category` 파라미터가 추가된 것을 확인할 수 있다.

```http
GET /filter?category=Gifts
```

![[Pasted image 20260902165006.png]]


앞서 배경 지식에서 살펴본 것처럼 웹 애플리케이션에서는 사용자가 전달한 값을 데이터베이스 조회에 사용할 수 있다.

여기서 확인할 수 있는 점은 다음과 같다.

- 상품을 카테고리별로 필터링하는 기능이 존재한다.
- 선택한 `Gifts` 값이 `category` 파라미터를 통해 서버로 전달된다.
- `category`의 값은 사용자가 변경할 수 있는 입력값이다.

> **그렇다면 서버는 `category`로 전달받은 값을 어떻게 처리하고 있을까?**

### 4.2 가설

`category`에 전달한 값에 따라 화면에 표시되는 상품이 달라지는 것을 확인했다.

따라서 서버가 `category` 값을 **상품 조회 조건으로 사용하고 있을 가능성**이 있다.

서버에서는 전달받은 `category` 값을 이용하여 다음과 같은 Query를 구성하고 있을 것으로 예상할 수 있다.

```sql
SELECT *
FROM products
WHERE category = 'Gifts';
```

만약 `category`의 값이 별도의 안전한 처리 없이 SQL Query에 사용되고 있다면,

> **사용자 입력을 통해 `WHERE` 절의 조건에 영향을 줄 수 있을 것**

이라고 가정했다.

### 4.3 검증

#### 4.3.1 작은따옴표 입력

`category` 값이 SQL Query에 사용되고 있는지 확인하기 위해 작은따옴표(`'`)를 입력해보았다.

![[Pasted image 20260902165837.png]]

그 결과 정상적인 상품 목록 대신 `Internal Server Error`가 발생했다.

작은따옴표(`'`)는 SQL에서 문자열을 구분하는 데 사용된다.

따라서 입력한 `'`가 SQL Query에 영향을 주어 **문법 오류가 발생했을 가능성**을 생각해볼 수 있다.

> **하지만 오류가 발생했다는 사실만으로 `category` 값이 SQL Query에 그대로 사용된다고 단정할 수는 없다.**

따라서 입력값이 실제로 SQL Query의 구조에 영향을 줄 수 있는지 추가적인 검증이 필요하다.

#### 4.3.2 작은따옴표 두 개 입력

작은따옴표(`'`) 하나를 입력했을 때는 `Internal Server Error`가 발생했다.

그렇다면 작은따옴표를 두 개(`''`) 입력했을 때는 어떻게 동작하는지 확인해보았다.

![[Pasted image 20260902171519.png]]

그 결과 서버가 다시 정상적으로 응답하는 것을 확인할 수 있었다.

서버가 다음과 같은 형태로 Query를 구성한다고 가정하면,

```sql
SELECT *
FROM products
WHERE category = '''';
```

작은따옴표 하나를 입력했을 때는 오류가 발생했지만, 두 개를 입력했을 때는 정상 응답이 반환되었다.

> **이를 통해 `category` 입력값이 SQL 문자열 구문에 영향을 주고 있을 가능성이 높다고 판단했다.**

#### 4.3.3 조건 조작

앞서 확인한 내용을 바탕으로 SQL Query의 조건을 변경해보았다.

사용자가 입력한 `category` 값이 SQL Query의 문자열 내부에 포함되는 것으로 추정했기 때문에, 조건식이 항상 참이 되도록 다음 값을 입력하였다.

```sql
' OR 1=1 --
```

정상적인 요청에서는 특정 카테고리에 해당하는 상품만 조회된다.

하지만 위 입력값이 SQL Query에 포함되면 **기존 문자열을 종료한 뒤 `OR 1=1` 조건이 추가**된다.

`1=1`은 항상 참이므로 기존 카테고리 조건과 관계없이 조회 조건 전체가 참이 될 수 있다.

또한 `--` 이후의 구문은 주석으로 처리되어 기존 Query의 나머지 부분이 실행에 영향을 주지 않도록 한다.

![[Pasted image 20260902174049.png]]

실행 결과, 기존에는 표시되지 않던 상품까지 조회되었으며 문제가 해결된 것을 확인할 수 있었다.

이를 통해 `category` 파라미터의 입력값이 SQL Query의 구조에 직접 영향을 줄 수 있으며, 해당 지점에 **SQL Injection 취약점이 존재한다는 것을 확인하였다.**

### 4.4 결과

입력값에 따른 응답 변화를 비교한 결과, `category` 파라미터의 값에 따라 서버의 응답이 달라지는 것을 확인하였다.

| 입력값 | 서버 응답 | 판단 |
| --- | --- | --- |
| 정상 값 | 정상 응답 | 정상적인 카테고리 조회 |
| `'` | `Internal Server Error` | SQL 문자열 구문에 영향을 줄 가능성 |
| `''` | 정상 응답 | SQL 문자열 처리와 관련된 정황 확인 |
| `' OR 1=1 --` | 숨겨진 상품까지 조회 | SQL 조건 조작 가능 |

작은따옴표(`'`) 하나를 입력했을 때 오류가 발생하고, 작은따옴표 두 개(`''`)를 입력했을 때 정상적으로 조회되는 것을 통해 사용자 입력값이 서버에서 실행되는 SQL 구문에 영향을 미치고 있음을 확인하였다.

이후 조건을 조작하여 숨겨진 상품까지 조회할 수 있었으며, 이를 통해 해당 파라미터에 **SQL Injection 취약점이 존재한다고 판단하였다.**

## 5. 원인 분석

정상적인 요청에서 서버가 다음과 같은 형태의 SQL Query를 실행한다고 가정할 수 있다.

```sql
SELECT *
FROM products
WHERE category = 'Gifts';
```

여기서 앞서 테스트한 것처럼 작은따옴표(`'`)를 입력하면 Query는 다음과 같이 구성될 수 있다.

```sql
SELECT *
FROM products
WHERE category = ''';
```

이 경우 작은따옴표의 개수가 맞지 않아 SQL 구문 오류가 발생할 수 있으며, 앞서 확인한 `Internal Server Error`와 같은 비정상적인 응답으로 이어질 수 있다.

여기서 확인할 수 있는 문제점은 다음과 같다.

1. **사용자의 입력값을 SQL 구문의 일부로 직접 결합하여 Query를 생성하는 것**
2. **SQL 실행 과정에서 오류가 발생했을 때 적절한 예외 처리가 이루어지지 않아 비정상적인 응답이 외부에 드러나는 것**

실제 서버의 소스코드는 확인할 수 없지만, 관찰된 동작을 바탕으로 사용자 입력값이 다음과 같이 SQL Query에 직접 결합되는 구조라고 추측할 수 있다.

```java
String category = request.getParameter("category");

String query =
    "SELECT * FROM products WHERE category = '" + category + "'";
```

위 코드에서는 사용자가 입력한 `category` 값이 SQL Query 문자열에 직접 결합되고 있다.

이 경우 사용자가 입력한 값이 단순한 **데이터**로 처리되는 것이 아니라 **SQL 구문의 일부**로 해석될 수 있다.

따라서 작은따옴표와 같은 SQL 문법 요소를 포함한 입력을 전달하면 기존 Query의 구조에 영향을 줄 수 있다.

> **Root Cause**
>
> 이번 취약점의 근본적인 원인은 **사용자 입력값과 SQL 구문이 명확하게 분리되지 않은 상태에서 Query가 생성된다는 점**이다.

또한 SQL 오류가 발생했을 때 응답의 차이가 외부에 드러나기 때문에 공격자가 입력값에 따른 변화를 관찰하고 취약점 존재 여부를 판단하기 쉬운 상태였다.

## 6. 대응 방법

SQL Injection을 방지하기 위해서는 **사용자 입력값을 SQL Query 문자열에 직접 결합하지 않아야 한다.**

가장 기본적인 대응 방법은 **Prepared Statement 또는 Parameterized Query**를 사용하여 SQL 구문과 사용자 입력값을 분리하는 것이다.

예를 들어 Java에서는 다음과 같이 작성할 수 있다.

```java
String sql = "SELECT * FROM products WHERE category = ?";

PreparedStatement pstmt = connection.prepareStatement(sql);
pstmt.setString(1, category);

ResultSet rs = pstmt.executeQuery();
```

위와 같이 Query 구조를 미리 정의하고 사용자 입력값을 별도의 파라미터로 전달하면, 입력값에 작은따옴표나 SQL 문법이 포함되어 있어도 **SQL 구문의 일부가 아닌 데이터로 처리**된다.

따라서 사용자가 입력값을 조작하여 기존 `WHERE` 절의 조건이나 SQL Query 구조를 변경하는 것을 방지할 수 있다.

추가적으로 다음과 같은 보안 조치를 함께 적용할 수 있다.

- **예외 처리**
  - SQL 실행 중 오류가 발생하더라도 데이터베이스 오류 정보가 사용자에게 직접 노출되지 않도록 처리한다.

- **입력값 검증**
  - 입력값의 형식이나 허용 가능한 값이 정해져 있다면 화이트리스트 기반으로 검증한다.

> **핵심 대응**
>
> 입력값 필터링에만 의존하는 것이 아니라 **Prepared Statement를 사용하여 SQL 구문과 사용자 데이터를 구조적으로 분리하는 것**이 중요하다.

## 7. 정리

이번 실습을 통해 SQL Injection의 기본 개념과 `WHERE` 절을 이용한 조건 조작에 대해 알아보았다.

작은따옴표(`'`)를 입력하여 사용자 입력값이 SQL 구문에 영향을 미치는지 확인하였고, `' OR 1=1 --`과 같이 항상 참이 되는 조건을 추가하여 기존 `WHERE` 절의 조건을 우회하고 숨겨진 상품까지 조회할 수 있었다.

이번 실습의 흐름을 정리하면 다음과 같다.

```text
category 파라미터 관찰
        ↓
SQL Query 사용 가능성 가설 수립
        ↓
' 입력 → 오류 발생
        ↓
'' 입력 → 정상 응답
        ↓
SQL 문자열 구문에 영향을 주는 정황 확인
        ↓
' OR 1=1 -- 입력
        ↓
WHERE 조건 조작
        ↓
숨겨진 상품 조회
        ↓
SQL Injection 확인
```

이러한 취약점은 사용자 입력값을 SQL Query에 직접 결합할 경우 발생할 수 있으며, **Prepared Statement를 사용하여 SQL 구문과 사용자 입력값을 분리하는 것이 중요하다.**
